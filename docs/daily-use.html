Daily use#

After forja init, two commands keep working inside the project: forja add writes new pieces of the hexagon in the right place with a passing test, and forja doctor checks that your machine and the project are in shape.

Both read forja.config.json. Run them anywhere inside the project; forja walks up the directories until it finds that file. Outside a project you get:

forja add#

The argument is <module>/<Name>. forja turns the name into PascalCase (place-order and placeOrder both become PlaceOrder) and the module into lowercase letters and digits (Order-Items becomes orderitems). On Node, a trailing UseCase is dropped, so PlaceOrderUseCase does not become PlaceOrderUseCaseUseCase.

usecasemodule requiredmodule required
entitymodule optional, and not used in the pathmodule required
portmodule optional, and not used in the pathmodule required

Where the files land on Node#

Everything goes into packages/core.

CommandCreatedUpdated
add usecase orders/PlaceOrdersrc/application/orders/PlaceOrderUseCase.ts, tests/unit/orders/PlaceOrderUseCase.test.tssrc/index.ts, src/infrastructure/config/container.ts
add entity Ordersrc/domain/entities/Order.ts, tests/unit/Order.test.tssrc/index.ts
add port OrderRepositorysrc/ports/IOrderRepository.ts, src/infrastructure/database/repositories/InMemoryOrderRepository.tssrc/index.ts
add port PaymentGatewaysrc/ports/IPaymentGateway.ts, src/infrastructure/adapters/InMemoryPaymentGateway.tssrc/index.ts

A port whose name ends in Repository gets its adapter in infrastructure/database/repositories/; any other port gets it in infrastructure/adapters/.

The use case is exported from the core's index.ts and registered in buildContainer() in container.ts, as placeOrderUseCase: new PlaceOrderUseCase(). forja edits the container through its syntax tree, so your own layout and comments stay as they are. If container.ts has no buildContainer() that returns an object, forja stops and tells you the line to add by hand.

The use case returns a Result and its test checks result.ok. The entity has create(), fromPersistence() and toPersistence(), and its test checks the round trip.

Where the files land on Java#

Everything goes into one module of apps/api. With com.shop as the root package, main/ below stands for apps/api/src/main/java/com/shop/orders/ and test/ for apps/api/src/test/java/com/shop/orders/:

CommandCreatedUpdated
add usecase orders/PlaceOrdermain/application/PlaceOrder.java, test/application/PlaceOrderTest.javamain/infrastructure/config/OrdersConfiguration.java
add entity orders/Ordermain/domain/Order.java (a record), test/domain/OrderTest.javanothing
add port orders/OrderRepositorymain/application/port/OrderRepository.java, main/infrastructure/persistence/InMemoryOrderRepository.javanothing
add port orders/PaymentGatewaymain/application/port/PaymentGateway.java, main/infrastructure/adapters/InMemoryPaymentGateway.javanothing

As on Node, a Repository port gets its adapter in persistence/ and any other port in adapters/.

The use case carries no annotations. forja adds a bean for it to <Module>Configuration in the module's infrastructure/config, and creates that class the first time the module gets a use case:

On Quarkus the method is a CDI producer (@Produces @ApplicationScoped) instead of a @Bean. The in-memory adapter is a Spring @Component or a Quarkus @ApplicationScoped bean. All of this keeps the ArchUnit rules green.

Nothing is overwritten#

If any file forja would create already exists, the command stops before writing anything:

Every check runs first, then every file is written at once, so a refused add leaves the project as it was.

After each command, forja prints the next step: npm test on Node, npm run test:api on Java, or, for a port, "give the port its first method, then pass it to the use case that needs it".

forja doctor#

The core-imports check reads every .ts and .tsx file under packages/core/src. It fails if any of them imports next, react, react-dom, react-native or expo, or if a file in domain/, application/ or ports/ imports from infrastructure/. It names the file and line.

A missing .env is a warning, because the code has defaults. Each failed or warned check prints the command or edit that fixes it:

The last line sums up: Ready, Ready, with 1 to look at, or 2 to fix, 1 to look at. forja doctor exits with code 1 when at least one check fails, and 0 otherwise, so you can use it in a script.

Directories named node_modules, .git, .next, .expo, dist, target and build are skipped.
