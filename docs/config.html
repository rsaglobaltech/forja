Configuration#

Every project forja creates has a forja.config.json at its root. It records the choices made at forja init, and forja add and forja doctor read it to know the backend, the package and the extras. You can also write one by hand, or copy one from another project, and pass it to forja init --config.

arch, ui, edgeFunctions and eas have one accepted value today. They hold the place of options forja does not generate yet, and a hand-written file must still include them.

What each field means:

  • scope names the internal packages: @shop/core, @shop/shared, @shop/web.
  • platforms lists the apps. On Java, [] means an API only.
  • backend decides where the logic lives: packages/core in TypeScript, or apps/api in Java.
  • javaPackage is the root Java package. Without it, forja uses com.<name> with the hyphens removed.
  • archunit adds the ArchUnit test on Java.
  • db: none keeps the in-memory repositories; postgres-docker adds PostgreSQL in Docker.
  • auth: sessions is the built-in session auth on Node; oauth2 is Keycloak and Auth.js on Java.
  • mailer: console prints emails to the terminal. It is used by Node sessions.
  • design: tailwind adds Tailwind on the web and NativeWind on mobile, with shared design tokens.
  • tests picks the test suites; e2e-web adds Playwright. See End-to-end tests.
  • extras: lint adds ESLint and Prettier, ci a GitHub Actions workflow, docker production Dockerfiles (Java), specgate the Specgate setup (forja and Specgate).
  • pm is the package manager forja installs with and forja doctor checks.

The same cross-field rules as the flags apply; CLI reference lists them with their messages.

Neither set turns on ci. It writes a GitHub Actions workflow, which spends Actions minutes on a private repository, so you ask for it.

Starting from a file#

forja reads and validates the file, then applies the name argument and the flags on top:

  • The name argument replaces name. If the file's scope was @<old name>, it becomes @<new name>; a custom scope stays.
  • --platforms, --db, --auth, --mailer, --design, --tests, --extras, --pm and --java-package replace the file's value. List flags replace the whole list.
  • --archunit and --no-archunit apply when the file's backend is Java.
  • --backend replaces the file's backend. The rest of the file must suit the new backend: auth: sessions with --backend spring is rejected.

The result is validated again, so a flag that breaks a rule is reported like any other.

--config asks nothing: like --yes, it installs the dependencies and runs git init unless you pass --skip-install or --skip-git.

Inside a project#

forja add and forja doctor look for forja.config.json in the current directory and its parents, and validate it. If you edit it by hand and break a rule, they stop with forja.config.json is not valid: and the problem. Changing a field does not regenerate anything; it only changes what add and doctor assume.
