forja and Specgate#

Specgate keeps a project's requirements, their scenarios and the tests that prove them in step. forja can generate a project ready for it, and forja add usecase links each new use case to its requirement. This page covers what forja does; the Specgate documentation covers Specgate itself.

Turn it on#

Specgate comes with the specgate extra. It is on by default for Java backends. On Node, ask for it:

In the wizard, tick "Specgate (spec-driven development)" under Extras.

docs/brief.md starts with four fields for Specgate, then a space for the client's brief:

Paste the brief below that block as you received it. Specgate checks that every value in a scenario comes from this text or from assumptions.md.

Adoption after the install#

When forja installs the dependencies, it adopts Specgate in the new project:

The third line puts the architecture in the gate: specgate check, specgate done and the harness run npm run arch between the specification and the tests, so code in the wrong layer fails the gate even when every test passes. On Node, npm run arch checks the core's import rules; on Java it runs the ArchUnit test alone. It needs Specgate 0.20 or newer; an older one leaves the gate as it was.

With git on, it commits the result as chore: adopt Specgate. If you used --skip-install, or the adoption failed (no network, for example), forja prints those commands among the next steps instead. Either way, the next steps end with:

forja doctor warns until the project is adopted, which it detects by the presence of spec.md and docs/specs/traceability.md.

Module by module#

The flow below is the one in the generated docs/specgate.md. Run npx specgate on its own whenever you lose track: it shows where the specification stands and the command to run next.

  1. Write the brief. Paste the client's brief into docs/brief.md and fill in the four fields. npx specgate draft explains each field; npx specgate draft --agent "claude -p" lets your agent propose them.

  2. Draft a module. Your agent writes the requirements and scenarios, and Specgate checks them against the brief:

    Without an agent, npx specgate draft orders prints the line to paste into one. Repeat until it says Ready to review.

  3. Review it with whoever knows the business. The open questions go to the client.

  4. Archive it. The requirements join the specification:

  5. Build each requirement, test first. A test that names REQ-007 is the link. forja add usecase writes the use case and that test for you; see the next section.

  6. Close the requirement. Specgate refuses while the suite is red:

  7. Before every pull request, run the gate:

Each module of the specification is a hexagonal module of the code: application/<module>/ in packages/core on Node, apps/api/.../<module>/ on Java.

forja add usecase with Specgate#

In a project where Specgate is adopted, forja add usecase also creates the requirement:

  1. forja checks first that no file would be overwritten, so a refused command leaves no orphan requirement.

  2. It runs specgate new "Place order". The title comes from the class name, or from --title.

  3. It writes the use case and its test, with the new id in the test's name:

    On Java, the id goes in @DisplayName("REQ-003 Place order"), and the pending scenario is a @Disabled test. The use case's comment says Specified by REQ-003.

  4. It runs specgate matrix to regenerate the traceability matrix, so specgate check sees the link.

The output names the requirement, the scenario file when Specgate reports one, and the next step:

The options#

OptionEffect
--req REQ-007names an existing requirement instead of creating one. The id must look like REQ- followed by digits.
--title "Place an order"the title specgate new gets, and the one in the test name
--no-specno requirement and no id in the test
--dry-runshows the files; creates no requirement

--req works for requirements that came out of specgate draft: the archived module already has REQ-007, and you want the code for it.

If Specgate cannot write the requirement, forja still writes the files and warns No requirement linked: with the reason.

In CI#

With the ci extra too, the generated GitHub Actions workflow has a spec job that runs npx -y @rsaglobaltech/specgate@0.19.1 validate . --strict. The tests themselves run in the other jobs.
